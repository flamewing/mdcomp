# Nemesis Nibble-Run Parsing Improvement Plan

Status: proposed investigation and implementation plan. Codec changes remain
subject to the testing and buffer prerequisites in
[`codec-implementation-plan.md`](codec-implementation-plan.md).

This plan expands the parse-side portion of the broader
[Nemesis algorithm research](codec-implementation-plan.md#nemesis-algorithm-research).
It defines a practical, strictly improving search strategy. It does not claim
global optimality for the joint parse, code-table, and container problem.

## Objective

Replace or augment Nemesis's maximum-run greedy parse with a deterministic
parser that accounts for the file-specific code table and complete encoded
size.

The current encoder splits every natural same-nibble run into tokens containing
at most eight nibbles, taking eight whenever possible. For example, a run of 18
identical nibbles becomes `8 + 8 + 2`. This minimizes the number of run tokens
locally, but Nemesis assigns file-specific, length-limited prefix codes to
symbols of the form:

```text
(nibble value, run length), where 1 <= run length <= 8
```

The parse determines the symbol frequencies, and those frequencies affect the
code table. A parse with more tokens can therefore be smaller when it
concentrates usage into a few reusable symbols. For natural runs of lengths
18, 5, and 20 for one nibble, the current parse produces:

```text
18 = 8 + 8 + 2
 5 = 5
20 = 8 + 8 + 4
```

The length histogram is `{8: 4, 2: 1, 5: 1, 4: 1}`. A coherent length-five
parse instead produces:

```text
18 = 5 + 5 + 5 + 3
 5 = 5
20 = 5 + 5 + 5 + 5
```

Its histogram is `{5: 8, 3: 1}`. Despite using more tokens, the repeated
length-five symbol may receive a short code while the remainder is encoded
inline.

## Confirmed Current Behaviour

The implementation in [`src/lib/nemesis.cc`](../src/lib/nemesis.cc) currently:

- pads input to a multiple of 32 bytes;
- evaluates both the normal and progressive-XOR transforms;
- greedily ends a nibble run when its encoded repeat count reaches seven,
  thereby limiting tokens to eight nibbles;
- builds the initial histogram from those already-split tokens;
- excludes frequency-one symbols from the initial code candidates;
- tries two node-ordering heuristics for each transform;
- estimates table, payload, and byte-rounding costs;
- creates supplementary "fake" code-map entries by partitioning an uncoded
  token into smaller coded tokens.

The supplementary entries can improve the encoding of a greedy token of up to
eight nibbles, but they cannot move a boundary introduced by the initial greedy
split. They also combine parsing decisions with code lookup and size
estimation. The new design should separate these concerns.

Before changing behaviour, add fixtures that exercise each item above and
capture the exact bytes generated by all four current candidates.

The captured Sega Retro revision independently describes the parse/code-table
coupling that motivates this plan. It also states that Sega's original
compressor used Shannon-Fano coding, specifically Fano's method and a
selection-sort assignment, rather than the package-merge strategy used by the
current mdcomp encoder. Reproducing Sega output and minimizing output size are
therefore separate objectives. Any compatibility mode needs its own algorithm,
tie-breaking rules, reference implementation, and byte-exact fixtures.

The reference also describes payload termination by the decompressed pattern
count in the two-byte header. The `0xff` byte terminates the code-table
description, not the encoded payload. Preserve that distinction in the
normative grammar and exact-size model.

## Optimization Model

Treat encoding as three coupled layers:

1. **Parse:** partition each maximal natural run into legal lengths 1 through
   8.
2. **Code table:** choose real table symbols and their code lengths from the
   parse histogram.
3. **Container:** serialize the table and payload, including mode, header,
   escape tokens, and final byte padding.

For a parse `P` and real code table `C`, compare the exact complete size:

```text
F(P, C) =
    two-byte file header
  + nibble-selection bytes in the code table
  + two bytes per real table symbol
  + one-byte table terminator
  + encoded payload bits
  + final byte padding
```

The payload cost of a token `(N, k)` is its real code length when it belongs to
`C`, or 13 bits otherwise: a six-bit escape, a three-bit repeat count, and a
four-bit nibble value.

Size estimation must be pure: it must not mutate the real code table by adding
supplementary entries. Before it controls selection, compare the estimator
against the number of bytes actually emitted for every test corpus entry and
deterministic randomized case.

The existing table builder is not assumed to solve the complete fixed-parse
problem exactly. Its package-merge step addresses bounded code lengths for a
fixed candidate alphabet, while symbol filtering, reserved-code handling, and
table-entry selection add further decisions. Initially, use the validated
current builder behind an explicit interface. Improve or replace it as a
separate work item in the parent plan.

## Canonical Maximal-Run Representation

Unpack each selected input transform into unrestricted maximal natural runs:

```text
(N0, L0), (N1, L1), ...
```

where adjacent runs have different nibbles and `Li` is not capped at eight.
These runs remain the canonical source throughout optimization. A candidate
parse stores a partition of each `Li` into legal token lengths.

Never optimize only the residual pieces of a previous parse. Whenever costs or
the active symbol set change, reparse every original maximal run from scratch.
This permits transitions such as:

```text
8 + 8 + 1  ->  6 + 6 + 5
5 + 5 + 5 + 3  ->  6 + 6 + 6
```

Provide an adapter from a selected partition to the ordinary legal tokens used
by the emitter. Reproducing the old maximum-eight partition through this
adapter must initially generate byte-identical output.

## Exact Parsing for a Fixed Table

For a fixed real table `C`, define:

```text
wC(N, k) = code_length_C(N, k), if (N, k) has a real table code
           13,                   otherwise
```

For a maximal run `(N, L)`, use the dynamic program:

```text
D[0] = 0
D[j] = min(D[j - k] + wC(N, k))
       for 1 <= k <= min(8, j)
```

Store predecessor choices to reconstruct the partition. This is a shortest
path over positions `0..L` with forward edges of lengths 1 through 8. Its time
is `O(8L)` and the total time of a parse pass is linear in the padded input
size.

Use deterministic lexicographic tie-breaking. The initial order should be:

1. lower payload bit cost;
2. fewer inline tokens;
3. fewer total tokens;
4. greater use of real table symbols;
5. longer token first at the earliest differing boundary.

Tie-breaking cannot make the fixed-table payload worse, but it can change the
next histogram. Record tie statistics so corpus evidence can determine whether
additional criteria or a small beam are worthwhile.

## Alternating Parse and Table Optimization

For each initial parse, alternate:

```text
parse -> histogram -> real table -> fixed-table reparse
```

A robust relaxation loop is:

```text
state = seed
best = exact legacy or seed candidate
seen = {}

repeat up to the configured iteration cap:
    table = build_table(state.parse_histogram)
    candidate = reparse_all_maximal_runs(table)
    candidate_size = emit_or_exactly_measure(candidate, table)
    retain candidate if it improves the deterministic best ordering

    stop if (candidate parse, real table) has been seen
    stop if the state is unchanged
    otherwise continue from candidate
```

When the fixed-parse table builder and the fixed-table parser are exact for
their respective subproblems, each accepted coordinate step should not
increase its corresponding objective. The present table builder has not yet
earned that assumption, and byte padding can hide payload changes. Therefore:

- measure the complete emitted size at state boundaries;
- retain the best state encountered rather than merely the last state;
- detect repeated states and impose a deterministic iteration cap;
- never discard the exact current encoder result as a fallback candidate.

This is alternating local optimization over a non-convex problem. Different
seeds may converge to different fixed points, and no result should be described
as globally optimal without the oracle and proof work in the parent plan.

## Deterministic Seed Portfolio

The maximum-eight parse is an essential baseline but a weak sole seed. A
symbol absent from that parse has an apparent cost of 13 bits and may never be
chosen, even if making it frequent would earn it a short table code.

Run at least these seeds independently for each input transform:

1. the current maximum-eight greedy partition;
2. a per-nibble dominant-length partition;
3. eight preferred-length partitions, one for each length 1 through 8;
4. a balanced partition that avoids small singleton remainders.

For a provisional preferred length `k`, assign:

```text
provisional_cost(j) = 1,  if j == k
                      13, otherwise
```

Then run the same maximal-run dynamic program under those costs. This is more
accurate than always taking `floor(L / k)` copies followed by one remainder:
the DP may find a cheaper partition of the remainder or avoid it by changing
earlier boundaries.

For a simple dominant-length estimate over runs `Li`, the provisional cost is:

```text
sum(floor(Li / k)) + 13 * count(Li mod k != 0)
```

when each nonzero remainder is treated as one inline token. Minimize this
quantity; do not treat the dominant-symbol frequency as a reward to maximize.
Prefer longer `k` only after provisional cost and the normal deterministic
tie-breakers are equal. The DP-based score is the authoritative seed
construction.

The seed score is only a bootstrap heuristic. Relax every seed fully and choose
by exact final output size. Also record cases where a worse initial seed
produces the best final result.

An optional later seed may use provisional Shannon-like costs derived from an
estimated histogram, but it is not required for the first implementation.

## Optional Search Enhancements

Add broader search only after the deterministic portfolio has corpus and
oracle results.

### Progressive symbol activation

There are only 128 real run symbols. Starting from a stable state, temporarily
assign an absent `(N, k)` an optimistic cost, reparse the maximal runs for
nibble `N`, rebuild the real table, and relax normally. Retain a trial only
when its exact final output wins under the deterministic ordering.

Rank candidates by measured final gain. Frequency alone is insufficient
because table bytes, nibble-selection bytes, displaced symbols, and padding can
reverse the result. Cache unaffected nibble runs and reject obviously
dominated trials only when the bound is documented.

After activation, optional neighbourhood moves may test removing an active
symbol or exchanging one active length for another. These moves must still
reparse original maximal runs.

### Histogram-distinct beam

Equal-cost fixed-table parses can produce different histograms and therefore
different next tables. If tie instrumentation and oracle comparisons show a
material gap, retain a small beam of equal- or near-cost states. Deduplicate by
parse histogram and real table, not only by current byte size.

Define a strict beam width, near-cost threshold, ordering, memory bound, and
iteration cap so output and runtime remain deterministic.

## Supplementary-Code Migration

The maximal-run parser generalizes the current supplementary "fake" codes:

- it handles natural runs of arbitrary length;
- it crosses former greedy boundaries;
- it may decompose a token even when a direct real code exists but is more
  expensive;
- it compares real codes and the 13-bit inline form uniformly.

Do not remove the supplementary machinery in the first behavioural patch.
Sequence the migration as follows:

1. isolate it from real table construction and exact size accounting;
2. prove that a maximal-run parse can reproduce every supplementary expansion;
3. compare emitted bytes and sizes with the legacy path;
4. retain the complete legacy encode as a candidate during corpus testing;
5. remove fake entries and the compile-time integer-partition tables only after
   there is no correctness or compression regression.

The final emitter should receive only legal run tokens. Each token is encoded
with either a real table code or the inline escape.

## Normal and Progressive-XOR Modes

Build maximal runs and run the complete seed portfolio independently for:

- the padded original nibble stream;
- the padded progressive-XOR nibble stream.

Do not reuse a histogram or preferred lengths across transforms. Select the
winner by complete emitted byte size, with a documented deterministic
tie-breaker. During migration, include all four existing transform/comparator
candidates in the final candidate set.

## Implementation Phases

### Phase 1: Baseline instrumentation

- [ ] Reconcile the Sega Retro description with the current decoder, recording
      discrepancies and source revisions.
- [ ] Add hand-authored vectors that distinguish the code-table terminator from
      pattern-count-driven payload termination.
- [ ] Decide whether Sega-compatible Shannon-Fano output is a separate mode or
      explicitly outside this shortest-output workstream.
- [ ] Record maximal-run distributions, greedy token histograms, real code
      lengths, inline-token counts, table bytes, payload bits, padding bits,
      total bytes, transform, and comparison strategy.
- [ ] Capture exact current output and round-trip results for the corpus.
- [ ] Add focused fixtures for each current heuristic and supplementary
      partition case.
- [ ] Establish deterministic runtime and compression baselines.

### Phase 2: Separate representations and cost accounting

- [ ] Introduce unrestricted maximal natural runs.
- [ ] Introduce an explicit legal-token parse and histogram type.
- [ ] Separate real table entries from supplementary expansions.
- [ ] Make exact size calculation pure and validate it against emitted bytes.
- [ ] Re-emit the legacy greedy parse byte for byte through the new types.

### Phase 3: Fixed-table dynamic parser

- [ ] Implement the per-run shortest-path recurrence.
- [ ] Cover every length and predecessor tie in unit tests.
- [ ] Reparse from original maximal runs rather than greedy fragments.
- [ ] Compare the DP with exhaustive partition enumeration on bounded runs.
- [ ] Run one post-table reparse while retaining legacy output as fallback.

### Phase 4: Alternating relaxation

- [ ] Rebuild histograms and tables after each parse.
- [ ] Track the best complete state and detect cycles.
- [ ] Define iteration limits and deterministic state ordering.
- [ ] Measure how often and how quickly relaxation converges.

### Phase 5: Multi-seed search

- [ ] Add the per-nibble dominant-length seed.
- [ ] Add the eight preferred-length seeds.
- [ ] Add a balanced-remainder seed.
- [ ] Compare final rather than initial seed sizes.
- [ ] Add pruning or seed reduction only when measurements preserve results.

### Phase 6: Oracle comparison and optional exploration

- [ ] Compare every strategy with the short-input exhaustive oracle from the
      parent plan.
- [ ] Classify remaining gaps as parse, table-selection, or local-search gaps.
- [ ] Add symbol activation or a bounded beam only for demonstrated gaps.
- [ ] Publish compression/runtime trade-offs and supported claims.

### Phase 7: Supplementary-code cleanup

- [ ] Prove coverage of all legacy supplementary expansions.
- [ ] Remove fake code-map entries from emission and estimation.
- [ ] Remove hard-coded or compile-time partition enumeration if unused.
- [ ] Re-run golden, corpus, oracle, sanitizer, and performance suites.

## Testing Strategy

### Correctness and compatibility

- round-trip normal and progressive-XOR streams;
- exact decoded-byte equality;
- exact legacy output when the legacy candidate wins;
- padded and already 32-byte-aligned inputs;
- natural runs of lengths 1 through 9 and substantially longer than eight;
- all 16 nibble values;
- inputs dominated by one nibble and highly fragmented distributions;
- payloads ending at every possible output-bit alignment;
- valid table symbols at code lengths 1 through 8 and inline-only parses;
- repeated-state and iteration-cap termination.

### Targeted adversarial inputs

Construct inputs where:

- a dominant length other than eight beats the greedy partition;
- a useful symbol is absent from the greedy histogram;
- an initially larger seed reaches a smaller fixed point;
- equal-cost parses create different next-generation tables;
- adding a table entry loses after header cost;
- payload savings are reversed by final byte padding;
- the preferred partition crosses one or more old eight-nibble boundaries;
- the progressive-XOR transform changes the best run-length distribution.

### Oracles and regression policy

- exhaustively enumerate legal partitions for bounded natural runs to validate
  the fixed-table DP;
- use the joint short-input oracle specified by the parent plan to measure,
  not conceal, the local-search gap;
- preserve the exact complete legacy encoder output as a candidate until the
  replacement is proven non-regressing on all maintained tests and corpora;
- require every reported improvement to be confirmed by actual emitted byte
  count and successful decoding.

### Performance

Measure total encode time, time per seed, parse passes, table builds, relaxation
iterations, optional-search trials, peak memory, and byte improvement. Report
both aggregate results and worst cases. Seed-level parallelism may be evaluated
later, but the first implementation should remain simple and deterministic.

## Success Criteria

The first implementation succeeds when it:

1. emits only valid, decoder-compatible Nemesis streams;
2. has a pure exact-size model that agrees with emitted byte counts;
3. can reproduce the legacy greedy parse and retains the legacy output
   candidate;
4. never increases selected output size on the maintained corpus;
5. improves at least one documented non-synthetic corpus case or a compelling
   adversarial fixture;
6. produces deterministic output for a fixed configuration;
7. has measured and acceptable encoding-time overhead;
8. reports its gap against the bounded exhaustive oracle without claiming
   unsupported global optimality;
9. makes the supplementary-code path removable or materially simpler.

The recommended first search configuration is:

```text
maximal natural runs
+ exact fixed-table dynamic parsing
+ alternating parse/table relaxation
+ a small deterministic seed portfolio
+ the complete legacy encoder as fallback
```

Progressive activation and beam search remain evidence-driven follow-up work.
